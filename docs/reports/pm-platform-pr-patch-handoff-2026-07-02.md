## Feature Summary

- Extends the single-project replacement module manager toward a configurable operations engineering management platform.
- Adds multi-project platform entry points and project-specific board/workbench behavior.
- Adds configurable project field concepts: primary field, aggregate field, child fields, import fields, site-capture fields, photo evidence, and required KPI fields.
- Adds graphical field configuration and workflow configuration surfaces for non-technical project operators.
- Separates import paths:
  - `initial_work_orders` enters the construction collection flow.
  - `external_completed` enters review/archive as a mid-project takeover path.
- Connects construction collection to configured checklist fields, photo slots, required platform KPI fields, and returned rework.
- Expands review workbench behavior around pending review, approved archive, returned rework, exception handling, and evidence checks.
- Adds project cockpit and project list KPI visibility for progress, delivery capability, review quality, and field evidence.
- Adds backend decomposition checkpoints so future agents can split work across field schema, workflow, import/template, construction/review, QA, and Ops lanes.
- Adds read-only platform persistence status and PostgreSQL persistence design, without creating or running a migration.
- Adds read-only project config persistence contract preview so reviewers can inspect how field schema and workflow definitions would map into future PostgreSQL tables before any migration is approved.
- Adds the persistence contract to the backend shared contract snapshot so route, target table, config record, round-trip, migration gate, and safety names remain stable across backend decomposition work.
- Adds read-only project readiness check so operators and future frontend panels can tell whether a project is ready for template import, construction collection, review, and delivery archive.
- Adds a frontend `上线检查` panel inside the existing field configuration dialog, consuming `GET /projects/{project_id}/readiness` without adding another row-level operation button.
- Adds Team Operating Model Lock documentation and a guard so the multi-agent team setting, dispatch packet, two-stage review gate, backend/frontend split, and next execution queue survive context compression.
- Adds a read-only `GET /projects/readiness/summary` endpoint, `action_counts`, and a `/platform-projects` `上线状态`/`接入待办` area so operators can scan which projects are `可接入` or `需补齐` and what to fix next without opening each field configuration dialog.
- Adds a clickable Project Readiness Action Filter: selecting a `接入待办` tag applies `filteredProjects`, shows `筛选中`, and `清除筛选` restores the full project list.
- Adds Project Persistence Readiness Frontend: the existing `字段配置` dialog shows read-only `持久化准备`, current storage, PostgreSQL migration approval state, target tables, round-trip status, and safety gates by consuming existing persistence endpoints.
- Adds Platform Migration Readiness Gate: `GET /projects/persistence/migration-readiness` and the `持久化准备` panel show backup, dry-run, verification, rollback, approval, and cutover-flag blockers; the gate keeps `ready_for_migration` false until a separate approved migration package exists.
- Adds Platform Handoff Readiness Summary: `GET /projects/handoff/readiness` aggregates readiness, persistence, migration gates, production safety, and next actions; the payload keeps `ready_for_review_package: true`, `ready_for_production_migration: false`, and `ready_for_production_release: false`; `/platform-projects` shows a top `交付就绪` band with `可评审包`, `production/V3/3.0.71`, and `生产迁移未放行`.
- Adds Platform LAN Tablet Access: `scripts/start-platform-local.ps1` defaults to `127.0.0.1`, supports explicit `-HostAddress 0.0.0.0` for trusted LAN tablet review, prints a `LAN URL`, and keeps production data/OSS/PostgreSQL untouched.

## 平台版本号评估

Recommendation: adopt an independent platform progress version such as `PM-V1.0.xx`.

- `PM-V1.0.xx` should describe only the project management platform development progress.
- Each platform PR/patch should pair the platform progress version with its production baseline, for example: `PM-V1.0.03, based on production V3.0.77`.
- `PM-V1.0.xx` must not replace, reserve, or consume official production `V3.0.xx` version numbers.
- Official production version numbers remain owned by the production maintenance line.
- This does not change the production version increment rules: small production changes still use `+0.01`, major workflow changes still need user confirmation before `+0.1`, and documentation/SOP-only changes do not bump the application version.
- Current status: keep this branch as a platform development branch until it follows `production/V3/3.0.77`; then choose the concrete platform progress value for the PR title/body.
