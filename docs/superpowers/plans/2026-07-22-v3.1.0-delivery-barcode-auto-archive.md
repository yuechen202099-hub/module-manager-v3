# V3.1.0 交付导出、条码核验与自动归档实施计划

> **执行要求：** 使用 `superpowers:subagent-driven-development` 逐任务实施；每个任务先写失败测试，再写实现；每个任务提交后独立审阅，最终再做全分支审阅。

**目标：** 在 `V3.0.84` 生产基线上完成双 Sheet 交付清单、新照片交付目录、资料组级条码/二维码/OCR 核验、证据变化失效、低负载后台扫描及核验通过后的事务性自动归档，并发布 `V3.1.0`。

**架构：** 保留现有施工上传、审阅、数据中台和驾驶舱接口的兼容字段，新建独立的资料组核验服务、持久化核验任务表和低负载工作器。`MaterialGroup.raw_data`/`Photo.raw_data` 中的旧结果只作为迁移输入和兼容输出，当前有效状态由关系表持久化；所有证据变化通过一个统一失效入口重新排队。正式交付包由独立导出服务一次性生成 `设备清单.xlsx` 和照片 ZIP，校验失败时不产生“看似成功”的交付包。

**技术栈：** FastAPI、SQLAlchemy 2、PostgreSQL、Alembic、openpyxl、Python ZIP、现有条码/二维码/OCR 识别器、Vue 3、Element Plus、systemd。

## 全局约束

- 分支固定为 `production/V3/3.1.0`，起点固定为已部署标签 `V3.0.84`。
- 不改变工单匹配、`00000000` 拦截、KPI、登录有效期、任务领取和审阅权限规则。
- 未匹配扫码必须提示“无工单”，禁止创建、显示或保存 `00000000`、全零或测试占位终端。
- 施工端自动上传保持关闭。
- 只有恰好四张有效照片且四个标准分类唯一完整的资料组才进入扫描。
- OCR 只能形成候选；未经人工确认不能自动通过、改写正式字段或自动归档。
- 后台识别一次只处理一个资料组；每批最多20组；批间暂停5秒；浏览器不得执行识别计算。
- 自动归档必须事务内复核、行锁保护、幂等并写审计；证据变化必须使旧核验失效。
- 迁移向后兼容，不删除历史核验或审计数据；发布时工作器初始暂停。
- 发布前备份 `.env`、`data`、`uploads` 和 PostgreSQL；成功后服务器仅保留最近5个发布目录。
