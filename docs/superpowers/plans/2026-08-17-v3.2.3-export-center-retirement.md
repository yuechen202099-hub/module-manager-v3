# V3.2.3 Export Center Retirement and OSS Migration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Retire every production export-center entry and server-side delivery artifact generator, safely migrate every active external photo to content-addressed OSS storage, and export selected data from OSS directly to the user's Windows computer.

**Architecture:** Apply a two-layer HTTP 410 gate at Nginx and at the start of FastAPI middleware, then disconnect the export router and remove all Vue export clients. Disable delivery-cache and delivery-package queue producers/consumers while preserving barcode verification and auto-archive. Add a separate single-worker external-photo migration CLI, a read-only server manifest signer, and a Windows-local downloader/composer.

**Tech Stack:** Python 3.11, FastAPI/Starlette, SQLAlchemy 2, PostgreSQL, oss2, Pillow, pytest, Vue 3, TypeScript, PowerShell, Nginx, systemd, openpyxl

**Spec:** <code>docs/superpowers/specs/2026-08-17-v3.2.3-export-center-retirement-design.md</code>

## Global Constraints

- Target version is exactly <code>3.2.3</code>; maintenance branch is <code>production/V3/3.2.3</code>.
- The fixed retirement copy is exactly: <code>导出中心已下线，请联系管理员由 OSS 导出到本机。</code>
- Nginx and FastAPI must return HTTP <code>410 Gone</code> for <code>/exports</code>, <code>/exports/*</code>, <code>/local-test/export-manifest/final-delivery</code>, <code>/local-test/unmatched/export</code>, and <code>/local-test/photo-barcode/review-groups/export</code>.
- The application 410 decision must happen before authentication, request validation, repository access, SQL, filesystem access, or export builders.
- Preserve PostgreSQL tables and historical rows; do not add an Alembic migration.
- Preserve existing OSS objects. The migration may create content-addressed objects but may not overwrite, move, or delete existing objects.
- Only active photos with <code>storage_type = 'external_url'</code> are migration candidates. Unknown storage types remain separately reported.
- External migration uses exactly one download/upload worker, a 30 MiB hard file limit, explicit host allowlist, DNS-pinned no-redirect HTTP, and short per-group database transactions.
- Migration start requires <code>MemAvailable >= 400 MiB</code> and temporary free space at least <code>512 MiB</code>; it stops below <code>250 MiB</code>, on a failed health probe/new OOM, or after five consecutive OSS errors.
- OSS-to-local export is read-only, defaults to at most four downloads, retries after 1/2/4 seconds, uses <code>.part</code> files plus atomic replacement, and never persists signed URLs in reports.
- Preserve construction upload, photo preview/review, barcode verification, auto-archive, KPI queries, data center, project board, and import-template download.
- Keep the Nginx 410 block in place when rolling the application back to V3.2.2.
- Protect unrelated staged work. Every commit must use <code>git commit --only -- &lt;explicit paths&gt;</code>.

- [ ] **Step 4: Implement the deterministic patcher**

Use a fixed block and refuse any shape other than two unpatched production <code>location /</code> markers:

~~~python
RETIREMENT_MESSAGE = "导出中心已下线，请联系管理员由 OSS 导出到本机。"
RETIREMENT_BLOCK = f"""
    location = /exports {{
        default_type application/json;
        return 410 '{{"detail":"{RETIREMENT_MESSAGE}"}}';
    }}
    location ^~ /exports/ {{
        default_type application/json;
        return 410 '{{"detail":"{RETIREMENT_MESSAGE}"}}';
    }}
    location = /local-test/export-manifest/final-delivery {{
        default_type application/json;
        return 410 '{{"detail":"{RETIREMENT_MESSAGE}"}}';
    }}
    location = /local-test/unmatched/export {{
        default_type application/json;
        return 410 '{{"detail":"{RETIREMENT_MESSAGE}"}}';
    }}
    location = /local-test/photo-barcode/review-groups/export {{
        default_type application/json;
        return 410 '{{"detail":"{RETIREMENT_MESSAGE}"}}';
    }}
"""

def patch_nginx_config(source: str) -> str:
    marker = "    location / {"
    if source.count("location = /exports") == 2:
        return source
    if source.count(marker) != 2:
        raise ValueError("expected exactly two production location / markers")
    return source.replace(marker, RETIREMENT_BLOCK + "\n" + marker)
~~~

The CLI accepts <code>--config</code> and <code>--output</code>, reads/writes UTF-8, and never writes in place.

def download_external_photo(
    source: ExternalPhotoSource,
    policy: DownloadPolicy,
    *,
    temp_dir: Path,
    opener: RemoteImageOpener = open_validated_remote_image_url,
) -> DownloadedPhoto:
    if policy.max_bytes != MAX_EXTERNAL_PHOTO_BYTES:
        raise ValueError("external photo max_bytes must be exactly 30 MiB")
    target = new_private_temp_path(temp_dir, source.photo_id)
    digest = hashlib.sha256()
    size = 0
    try:
        with opener(
            source.url,
            headers={"User-Agent": "module-manager-v3-external-photo-migrator/1.0", "Accept": "image/*"},
            timeout=policy.timeout_seconds,
            allowed_hosts=policy.allowed_hosts,
            app_env="production",
        ) as response, target.open("xb") as output:
            declared = parse_content_length(response.headers.get("Content-Length"))
            if declared is not None and declared > policy.max_bytes:
                raise PhotoTransferError("external photo is too large")
            while chunk := response.read(policy.chunk_bytes):
                size += len(chunk)
                if size > policy.max_bytes:
                    raise PhotoTransferError("external photo is too large")
                output.write(chunk)
                digest.update(chunk)
            output.flush()
            os.fsync(output.fileno())
            content_type = normalized_image_content_type(response.headers.get("Content-Type", ""))
        verified_type, verified_suffix = verify_image_file(target, content_type, size)
        return DownloadedPhoto(target, digest.hexdigest(), size, verified_type, verified_suffix)
    except BaseException:
        target.unlink(missing_ok=True)
        raise
~~~

def store_downloaded_photo(
    bucket: Any,
    bucket_name: str,
    key: str,
    photo: DownloadedPhoto,
) -> OssObjectReceipt:
    before = head_object_or_none(bucket, key)
    if before is not None:
        verify_object_meta(before, photo)
        return OssObjectReceipt(bucket_name, key, photo.sha256, photo.byte_size, photo.content_type, True)
    headers = {
        "Content-Type": photo.content_type,
        "x-oss-meta-sha256": photo.sha256,
        "x-oss-forbid-overwrite": "true",
    }
    try:
        bucket.put_object_from_file(key, str(photo.path), headers=headers)
    except Exception as exc:
        if not is_forbid_overwrite_conflict(exc):
            raise
        raced = head_object_or_none(bucket, key)
        if raced is None:
            raise OssVerificationError("concurrent OSS object is missing") from exc
        verify_object_meta(raced, photo)
        return OssObjectReceipt(bucket_name, key, photo.sha256, photo.byte_size, photo.content_type, True)
    after = head_object_or_none(bucket, key)
    if after is None:
        raise OssVerificationError("uploaded OSS object is missing")
    verify_object_meta(after, photo)
    return OssObjectReceipt(bucket_name, key, photo.sha256, photo.byte_size, photo.content_type, False)
~~~

~~~python
RETRY_DELAYS = (1.0, 2.0, 4.0)
MAX_DOWNLOAD_WORKERS = 4

def download_one(item: ManifestItem, output_root: Path, *, opener, sleeper) -> ItemResult:
    target = safe_output_path(output_root, item.relative_path)
    part = target.with_name(target.name + ".part")
    target.parent.mkdir(parents=True, exist_ok=True)
    for attempt in range(len(RETRY_DELAYS) + 1):
        try:
            digest = hashlib.sha256()
            size = 0
            with opener(item.download_url, timeout=30) as response:
                _validated_content_length(response, item.byte_size)
                with part.open("xb") as output:
                    while size < item.byte_size:
                        remaining = item.byte_size - size
                        chunk = response.read(min(1024 * 1024, remaining))
                        if not chunk:
                            break
                        next_size = size + len(chunk)
                        if next_size > item.byte_size:
                            raise ValueError("download response exceeds declared byte_size")
                        output.write(chunk)
                        digest.update(chunk)
                        size = next_size
                    output.flush()
                    os.fsync(output.fileno())
            if item.byte_size and size != item.byte_size:
                raise ValueError("byte size mismatch")
            if digest.hexdigest() != item.sha256:
                raise ValueError("sha256 mismatch")
            os.replace(part, target)
            return ItemResult.success(item, target, size)
        except Exception as exc:
            part.unlink(missing_ok=True)
            if attempt == len(RETRY_DELAYS):
                return ItemResult.failure(item, sanitize_error(exc))
            sleeper(RETRY_DELAYS[attempt])
    raise AssertionError("unreachable")
~~~

<code>_validated_content_length()</code> requires exactly one positive decimal <code>Content-Length</code> matching the manifest item before opening the part file. Each body read is capped to the remaining declared bytes, and any opener that returns more than requested fails before that chunk is written; the loop stops at the declared size rather than waiting for EOF. Thus every retry can write at most the already planned item size and a lying/non-ending response cannot grow the part file without bound. <code>run_export_stream()</code> parses only the URL-free header first, performs the disk gate, and then passes a lazy item iterator to <code>download_manifest()</code>. <code>download_manifest()</code> rejects <code>max_workers</code> outside 1–4, uses <code>ThreadPoolExecutor(max_workers=max_workers)</code>, and maintains at most <code>max_pending=8</code> submitted futures. It reads the next signed item line only when a pending slot opens, which creates backpressure on the Task 5 SSH pipe so short-lived URLs are signed close to use. It preserves stable manifest order in reports and never logs the signed URL. <code>run_export()</code> is exactly <code>run_export_stream(io.StringIO(stdin_text), ...)</code>; the CLI calls <code>run_export_stream(sys.stdin, ...)</code> directly.
