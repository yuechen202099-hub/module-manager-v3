# V3.0.84 任务领取与审阅工作台性能优化设计

## 1. 背景与目标

生产基线为 `V3.0.83`。本版本只处理两个性能问题：

1. 任务领取页加载过慢。
2. 审阅工作台加载过慢。

本版本不改变任务领取、释放、施工指派、改派、审阅、异常、扫码、人工确认和归档的业务口径，也不包含 `V3.1.0` 的交付导出与自动归档规则升级。

## 2. 已确认的瓶颈

### 2.1 任务领取页

- `ClaimTasksView.vue` 进入页面后先请求 `/local-test/tasks/status`，状态变化后再请求 `/local-test/tasks`，形成串行等待。
- `/tasks/status` 仍会遍历任务并聚合资料组统计，因此它不是低成本版本检查。
- `/tasks` 默认计算地址和表号聚合搜索文本，并计算安装人员分布；任务领取页并不展示安装人员分布。
- 浏览器虽有 `sessionStorage` 缓存，但每次进入仍触发服务端全量聚合，缓存只改善显示，不改善服务器负载。

### 2.2 审阅工作台

- `TaskHallView.vue` 先获取全部任务，再请求所选终端最多 `1000` 个资料组。
- PostgreSQL 的 `list_task_groups()` 当前先加载并构建全部资料组 payload，再在 Python 中切片，数据库分页参数没有真正限制前置计算量。
- 前端每分钟重新请求全部任务和当前终端全部资料组。
- 资料组列表在客户端完成筛选、计数和排序，数据量增长后网络传输、对象映射和 Vue 响应式开销同步增长。

## 3. 方案比较

### 方案 A：只增加前端缓存

改动最小，但服务端仍会执行全量聚合，无法解决服务器负载和首次打开慢的问题，不采用。

### 方案 B：只优化 SQL

可以降低单次请求成本，但每个访问者仍重复计算相同任务汇总，且审阅工作台仍传输过多资料组，不足以满足生产体验，不采用。

### 方案 C：服务端任务快照加审阅资料组真分页

任务列表由服务端周期生成共享快照，页面读取快照；审阅资料组由数据库先筛选、排序、分页，再构建当页数据。该方案同时降低首屏延迟、CPU、数据库压力和响应体积，作为本版本实施方案。

## 4. 服务端任务快照

### 4.1 快照内容

新增按 `team_id` 隔离的任务列表快照，内容包括：

- `items`：任务领取页和审阅工作台需要的任务字段。
- `version`：由快照内容生成的稳定版本摘要。
- `generated_at`：快照生成时间。
- `cache`：来源、是否陈旧、刷新周期等元数据。

任务快照保留地址与表号搜索能力，但不计算任务领取页未使用的安装人员分布。现有完整任务接口继续保留，避免影响其他页面。

### 4.2 刷新策略

- 服务启动后立即预热当前团队快照。
- 默认每 `60` 秒刷新一次。
- 快照过期时先返回旧快照，再在后台单线程刷新，不让访问请求等待全量聚合。
- 同一团队同一时刻最多存在一个刷新任务。
- 快照同时保存在内存和 `data` 下的持久化缓存文件，服务重启后可先返回最近一次快照。
- 管理员点击刷新时允许强制刷新；强制刷新失败时保留旧快照并提示，不清空页面。
- 团队之间禁止共享快照，缓存文件必须校验 `team_id`。

### 4.3 前端读取

任务领取页和审阅工作台统一调用任务快照接口：

- 页面先恢复现有 `sessionStorage` 数据，立即显示。
- 后台只发起一次快照请求，不再串行请求 `/tasks/status` 和 `/tasks`。
- 快照 `version` 未变化时不替换任务数组，减少 Vue 重算和页面闪动。
- 领取、释放、指派、改派和优先施工操作继续局部更新当前任务，随后静默请求快照确认。

## 5. 审阅资料组分页

### 5.1 接口契约

新增或扩展审阅资料组查询，支持：

- `limit`：固定上限 `20`。
- `offset`：页码换算后的偏移量。
- `status`：`all`、`reviewable`、`exception`、`archived`、`unconstructed`。
- `query`：表号、终端号、地址、模块号、采集器号搜索。
- 返回 `total`、`items`、`status_counts`、`limit`、`offset`。

搜索和状态筛选必须作用于整个终端资料组集合，而不是只搜索当前页。

### 5.2 PostgreSQL 查询原则

- 在数据库层完成团队、任务、状态和搜索过滤。
- 在数据库层完成审阅队列排序和 `LIMIT/OFFSET`。
- 只为当前20条资料组构建 payload。
- 当前页照片条码摘要使用一次批量查询，不允许逐资料组 N+1 查询。
- `status_counts` 使用聚合查询获得，不为计数构建完整资料组 payload。
- 为实际过滤和排序字段补充必要索引；新增索引必须通过迁移管理。

JSON 后端保持相同接口行为，允许在内存中过滤，但必须先生成轻量摘要，分页后才补当前页照片信息。

### 5.3 前端交互

- 资料组列表每页20条，增加标准分页控件。
- 切换任务、状态或搜索条件时回到第一页。
- 搜索输入防抖 `300` 毫秒，过期请求结果不得覆盖新请求。
- 打开资料组时只获取该组完整详情和四张照片。
- 可预取当前页第一条待审阅资料组详情，但禁止预加载整页原图。
- 审阅、异常、回退、扫码确认或归档后，仅刷新当前页和任务快照，不重新获取1000条资料组。
- 当前页最后一条处理完成且页面变空时，自动退到有效的上一页或加载下一批待审阅数据。

## 6. 后台刷新与容错

- 审阅工作台取消每分钟全量任务和全量资料组刷新。
- 每分钟只请求轻量任务快照；版本不变时不更新页面。
- 当前资料组发生写操作后，局部合并接口返回值，并静默刷新当前页。
- 快照刷新失败时继续显示上次数据，并保留手动刷新入口。
- 分页请求失败时保留当前页，不清空已显示资料。
- 所有请求继续遵守当天登录有效期和401自动跳转登录页规则。

## 7. 兼容性与非目标

- 保留原 `/tasks`、`/tasks/status` 和 `/tasks/{task_id}/groups` 行为，其他客户端不被强制迁移。
- 不改变任务完成率、可施工、可审阅、优先施工、扫码 `3/3` 和人工确认规则。
- 不在本版本执行历史条码扫描、自动归档或交付包格式变更。
- 不增加浏览器端扫码或 OCR 计算。

## 8. 测试策略

先补测试，再改实现。至少覆盖：

1. 同一团队连续读取任务快照只执行一次构建。
2. 快照过期时立即返回旧数据并只启动一个后台刷新。
3. 服务重启可读取持久化快照，且拒绝团队不匹配文件。
4. 强制刷新产生新版本，失败时旧快照仍可用。
5. 任务快照不计算安装人员分布但保留任务领取搜索需要的字段。
6. 任务领取页只发起一次快照请求，不再串行读取状态和任务。
7. 审阅工作台首次只请求20条资料组。
8. PostgreSQL 在 payload 构建前完成分页。
9. 状态计数覆盖完整筛选结果，不受当前页限制。
10. 搜索覆盖表号、终端号、地址、模块号和采集器号。
11. 快速切换任务、筛选和搜索时，旧请求不能覆盖新页面。
12. 写操作后只刷新当前页，不触发1000条全量请求。
13. 领取、释放、指派、改派、审阅、异常、回退和归档行为回归通过。

## 9. 性能验收

在生产数据快照或等量本地数据上记录优化前后数据：

- 任务快照热读取服务端耗时目标小于 `300ms`。
- 任务领取页有浏览器缓存时，主要列表目标在 `500ms` 内可见。
- 审阅工作台任务列表目标在 `1s` 内可见。
- 首个20条资料组列表目标在 `1.5s` 内可见。
- 单次资料组列表响应不得超过20条，不得请求 `limit=1000`。
- 同一团队任务聚合构建频率不超过每60秒一次，强制刷新除外。
- 后台刷新期间页面操作保持可用，接口错误不得清空当前列表。

性能目标作为发布门禁；若生产等量数据无法达到目标，继续优化查询或索引，不以功能测试通过替代性能验收。
