# 运维工程管理平台第一期设计

日期：2026-06-29

## 背景

当前系统主要服务“更换模块”项目，已经具备施工采集、照片审阅、任务领取、项目驾驶舱、导出等能力。后续目标是让网站不只管理这一个项目，而是逐步演进为可同步管理多个工程项目的运维工程管理平台。

第一期不做大规模重构，不迁移生产数据，不打断现有更换模块生产流程。第一期目标是在现有流程外层增加轻量平台视图，让管理员能从一个地方掌握项目进度、交付状态、现场采集、审阅质检和风险卡点。

## 第一目标

第一期选择“轻量任务中心”路线：

- 保留现有更换模块施工、审阅、照片、资料组、导出等主流程。
- 在外层新增平台汇总层和管理视图。
- 先让平台看得见进度、看得见交付、看得见风险。
- 不把现有业务模型强行替换为全新的通用任务模型。

短期优先级：

1. 项目进度
2. 项目交付能力
3. 现场施工同步数据采集
4. 审阅功能

## 范围

第一期包含：

- 项目总览页：展示所有项目的阶段、进度、风险和交付状态。
- 项目驾驶舱：展示单个项目的进度、任务、交付、现场采集、审阅质检和风险问题。
- 统一任务中心：汇总施工任务、审阅任务、异常处理任务和交付准备任务。
- 交付中心：管理交付清单和交付记录。
- 风险问题页：聚合现场异常、审阅未通过、交付缺项和长时间未处理任务。
- 管理员进度校正：允许管理员对系统自动进度进行人工调整、备注和锁定，并记录审计日志。
- 后端模块化基础：在新增平台能力时同步拆分后端边界，让项目、任务、交付、现场采集、审阅、风险和审计逐步形成独立模块。

第一期不包含：

- 不重写更换模块核心业务流程。
- 不迁移生产 PostgreSQL 数据。
- 不直接修改 OSS 生产对象。
- 不替换现有施工页面、审阅页面和导出能力。
- 不设计完整工作流引擎。
- 不把所有未来项目类型一次性抽象完成。
- 不一次性重构全部后端服务，不把现有大文件全部拆完后再上线。

## 平台定位

平台定位为“运维工程进度与交付平台”，不是单纯的项目管理系统。

平台第一价值是帮助管理员回答：

- 项目现在做到哪一步了？
- 哪些任务完成了，哪些卡住了？
- 哪些交付项已经准备好？
- 哪些现场异常或审阅问题影响交付？
- 当前管理口径和底层真实数据是否一致？

## 核心数据对象

第一期建立 6 个平台概念，作为现有业务数据之上的汇总层。

### Project 项目

项目是平台管理入口。当前“更换模块项目”是第一个项目，后续可以接入其他施工、维护、交付类项目。

### Project Stage 项目阶段

项目阶段用于表达管理口径下的项目状态。建议阶段包括：

- 准备中
- 施工中
- 审阅中
- 交付准备
- 待验收
- 已交付

阶段默认由系统根据施工、审阅、异常和交付状态自动汇总。管理员可以人工调整阶段、备注原因、锁定关键节点。

### Task 任务

任务是统一任务中心的基础单位。第一期任务不强制替换现有业务任务，而是从现有数据汇总得到。

任务类型包括：

- 施工任务
- 审阅任务
- 异常处理任务
- 交付准备任务

### Field Record 现场采集记录

现场采集记录包括：

- 施工状态
- 现场照片
- 异常说明
- 采集人
- 采集时间

现场采集是项目进度和交付证据的重要来源。

### Review Record 审阅记录

审阅记录第一期优先服务质量检查和交付前验收。

审阅结果包括：

- 通过
- 需返工
- 异常
- 不影响交付的备注问题

数据纠错能力保留，但不作为第一期平台主线。

### Delivery Item / Delivery Record 交付项和交付记录

交付项表示项目必须完成的交付清单。每个交付项有状态：

- 未开始
- 准备中
- 待确认
- 已通过
- 需返工

交付记录表示一次实际交付，包含：

- 交付时间
- 交付负责人
- 接收人
- 交付版本
- 关联导出文件或说明
- 验收结果
- 备注

第一期文件导出沿用现有能力，平台只引用导出结果或记录交付版本。

## 项目进度规则

项目进度采用“系统自动汇总 + 管理员人工校正”的双层模型。

### 系统进度

系统进度根据现有施工、审阅、异常和交付状态自动计算。

示例指标：

- 施工任务完成率
- 审阅通过率
- 异常未关闭数量
- 交付项完成率
- 长时间未更新任务数量

### 管理进度

管理进度用于对外展示和项目管理口径。管理员可以：

- 手动调整阶段
- 添加进度备注
- 锁定关键节点
- 标记“按管理口径已完成”

所有人工调整必须记录：

- 操作人
- 操作时间
- 调整前状态
- 调整后状态
- 调整原因

## 页面结构

### 项目总览页

展示所有项目的简要状态。

核心信息：

- 项目名称
- 当前阶段
- 系统进度
- 管理进度
- 交付状态
- 风险数量
- 最近更新时间

### 项目驾驶舱

单个项目的总控页面。

核心模块：

- 项目进度
- 任务完成情况
- 交付清单
- 现场采集摘要
- 审阅质检摘要
- 风险与卡点

### 统一任务中心

跨项目任务列表。

筛选维度：

- 项目
- 任务类型
- 状态
- 负责人
- 是否超时
- 是否影响交付

### 交付中心

管理交付清单和交付记录。

核心能力：

- 查看交付项
- 更新交付项状态
- 创建交付记录
- 关联现有导出文件或交付说明
- 标记验收结果

### 风险问题页

聚合所有影响项目推进和交付的问题。

风险来源：

- 现场异常
- 审阅未通过
- 交付清单缺项
- 长时间未处理任务
- 管理进度和系统进度不一致

## 数据流

第一期数据流为：

现有施工、审阅、导出数据 → 平台汇总层 → 项目驾驶舱、任务中心、交付中心、风险问题页

平台汇总层负责：

- 汇总现有业务状态
- 计算项目进度
- 生成任务中心视图
- 聚合交付状态
- 聚合风险问题

平台汇总层不负责：

- 替换现有资料组业务规则
- 改写照片审阅规则
- 改写施工采集主流程
- 直接修改生产 OSS 或 PostgreSQL 数据

## 后端模块化设计

第一期应在新增平台能力的同时拆分后端模块边界。目标不是立即完成全面重构，而是让新增代码不继续堆进已有大文件，并为后续多项目平台化留下稳定结构。

当前后端已有基础分层：

- `v2-api/app/api/routes/` 承载路由入口。
- `v2-api/app/services/` 承载业务服务。
- `v2-api/app/schemas/` 承载接口数据结构。
- `v2-api/app/db/` 承载数据库相关能力。

但服务层已经出现明显聚合文件，例如 `state_repository.py` 和 `local_simulation.py` 体量很大。第一期不应把平台能力继续叠加到这些大文件里。

### 建议模块边界

第一期新增能力按模块组织：

- `projects`：项目、项目阶段、项目总览。
- `progress`：系统进度计算、管理进度校正、阶段锁定。
- `tasks`：统一任务中心、任务类型、任务状态、负责人。
- `delivery`：交付清单、交付项、交付记录、交付版本。
- `field`：现场采集摘要、状态、照片、异常。
- `review`：审阅质检摘要、返工、交付前确认。
- `risks`：风险问题聚合、阻塞项、超时任务。
- `audit`：管理员人工调整、交付确认、关键状态变更留痕。
- `adapters`：从现有更换模块业务数据转换为平台汇总对象。

这些模块可以先以服务文件和路由文件的形式落地，不要求第一期立刻变成完整插件体系。

### 模块化原则

- 新平台接口不直接读写生产 OSS 对象。
- 新平台接口不绕过现有权限规则。
- 新平台汇总优先通过 adapter 读取现有业务状态，再输出统一项目、任务、交付和风险视图。
- 现有更换模块业务规则保留在原有链路中，平台模块通过清晰接口调用或汇总结果引用。
- 新增模块之间通过明确的数据结构通信，避免互相导入内部实现细节。
- 大文件拆分采用渐进方式：每次只抽离与当前平台功能直接相关的逻辑，并用测试保护现有行为。

### 第一阶段拆分重点

第一阶段优先拆出和平台外层直接相关的后端能力：

- 项目总览汇总服务。
- 项目进度计算服务。
- 管理进度校正和审计服务。
- 交付清单和交付记录服务。
- 风险问题聚合服务。
- 更换模块适配器，用于把现有施工、审阅、异常和导出状态映射到平台视图。

暂不优先拆分：

- 照片分类核心规则。
- 条码和 OCR 扫描核心规则。
- 总清单和资料组硬业务规则。
- 历史本地模拟流程中的全部测试辅助能力。

这些能力可以在后续平台任务核心稳定后继续分阶段整理。

## 权限设计

第一期权限保持保守。

### 管理员

可以：

- 查看所有项目
- 调整项目进度
- 锁定阶段
- 管理交付清单
- 创建交付记录
- 分配任务
- 查看风险问题

### 施工人员

可以：

- 查看自己相关的现场任务
- 提交施工状态
- 上传现场照片
- 提交现场异常

### 审阅人员

可以：

- 查看审阅和质检任务
- 提交通过、返工、异常意见
- 查看与审阅相关的交付前问题

### 只读角色

可以：

- 查看项目进度
- 查看交付状态
- 查看风险摘要

不可以：

- 修改任务
- 修改进度
- 修改交付记录
- 修改审阅结果

## 风险控制

第一期必须遵守生产边界：

- 不覆盖生产 `.env`。
- 不覆盖生产 `data`。
- 不覆盖生产 `uploads`。
- 不直接修改 OSS 生产对象。
- 不直接修改 PostgreSQL 生产数据。
- 发布前必须确认备份、验证和回滚路径。

实现时应优先通过新增汇总接口、只读视图或独立平台表承载新增能力，避免直接改动现有核心业务链路。

## 验证要求

第一期上线前至少验证：

- 现有更换模块施工页面不受影响。
- 现有审阅页面不受影响。
- 现有导出和交付文件能力不受影响。
- 项目驾驶舱能正确汇总施工、审阅、异常、交付状态。
- 系统进度和管理进度可以区分展示。
- 管理员人工调整进度会记录审计日志。
- 交付清单和交付记录可以按项目隔离。
- 新增后端平台能力按模块组织，不能继续把核心平台逻辑堆入 `state_repository.py` 或 `local_simulation.py`。
- 模块化拆分不改变现有施工、审阅、导出接口的行为。
- 权限隔离正确，施工、审阅、只读角色不能越权修改。
- 风险问题页能聚合现场异常、审阅未通过、交付缺项和超时任务。

## 分期建议

### 第一期

实现轻量任务中心和平台外层视图。

交付结果：

- 项目总览页
- 项目驾驶舱
- 统一任务中心
- 交付中心
- 风险问题页
- 管理进度人工校正和审计记录
- 后端平台模块边界和更换模块适配器

### 第二期

把第一期稳定下来的字段和规则沉淀为更通用的平台任务核心。

可能包含：

- 通用任务模型
- 项目模板
- 交付模板
- 跨项目统计
- 更细权限配置

### 第三期

根据新项目接入情况，逐步建设模块化平台能力。

可能包含：

- 不同项目类型的字段模板
- 工作流模板
- 移动端现场采集优化
- 客户只读门户
- 多项目交付报表

## 成功标准

第一期成功的标志不是“所有功能平台化”，而是：

- 管理员可以从一个入口看清项目进度。
- 管理员可以从一个入口看清交付状态。
- 现场异常和审阅问题会自动暴露为项目风险。
- 管理员可以按管理口径校正进度，并留下审计记录。
- 后端新增平台能力具备清晰模块边界，后续项目可以沿同一结构接入。
- 现有更换模块生产流程保持稳定。

## 待实施前确认

进入实施计划前，需要确认：

- 第一批页面是否按“项目总览、项目驾驶舱、任务中心、交付中心、风险问题页”展开。
- 第一批交付项模板是否先围绕更换模块项目制定。
- 管理员人工校正是否只允许管理员角色操作。
- 只读角色是否第一期就需要上线。
- 是否需要在第一期提供客户可看的只读链接，还是先做内部只读账号。
- 后端模块目录和命名是否采用 `projects/progress/tasks/delivery/field/review/risks/audit/adapters` 这一组边界。
