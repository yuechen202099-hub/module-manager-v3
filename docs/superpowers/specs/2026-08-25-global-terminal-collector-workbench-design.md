# 全局终端采集器翻拍工作台整合设计

## 1. 背景与目标

V3.2.8 已有项目级采集器扫码库存、一次性随机分配和翻拍工作台，但翻拍入口仍要求操作员先选择项目和运行批次，采集器替换也位于独立的批次管理页面。实际操作希望更短：打开翻拍工作台，直接搜索并选择当前施工数据中的终端，然后在终端内确认采集器“有实物、无实物、已替换”状态；管理员对全部无实物采集器执行一次原子替换。

本次调整的目标是：

- 翻拍工作台前台不再要求选择项目或批次，直接提供团队范围内的“可翻拍终端”。
- 项目和运行批次仍保留为服务端隔离及快照机制，绝不允许跨团队或跨项目使用采集器池。
- 同号扫码即证明手上有该实物，同号采集器不要求在网站拍照，也不进入随机替换池。
- 无同号实物的采集器可由管理员在终端内一键从所属项目采集器池随机替换；数量不足时整次零分配。
- 独立“替换池批次”页面退役，替换、查看和撤销都收口到翻拍工作台。
- 保留原始施工数据、分配记录、完成记录和审计链，支持受控撤销。

这仍是人工向甲方平台翻拍和录入的辅助系统。系统不登录、不调用、不填写、不自动上传甲方平台。

## 2. 已确认业务规则

1. 一个终端可带多块电能表；每块电表生成一条新装项。
2. 每条新装项严格只有两张照片：“电表和模块”和“改造完成”。
3. 拆旧采集器按终端内完整采集器号去重；同一采集器带多块表时只生成一个拆旧项。
4. 终端所需采集器数量等于该终端去重后的拆旧采集器数量。
5. 同号采集器是已经通过手机扫码确认在手的实物，显示“有实物”；无需在网站拍照，翻拍时直接对准实物。
6. 没有同号实物的采集器显示“无实物”；只有管理员可以执行替换。
7. 随机替换后显示“已替换”，并展示替换后的采集器号、Code 128 条码和池内实物照片。
8. 一次点击必须覆盖该终端当时全部“无实物”需求。池数量不足时不创建任何分配，不改变需求、实物或工作项状态。
9. 池内一个实物和一张有效照片只能被有效分配消费一次，禁止重复使用。
10. 随机结果一经提交必须持久化；刷新页面、并发请求或服务重启不能改变结果。
11. 采集器扫码库存不分批次；手机打开页面即可扫码。扫码阶段不录入甲方平台。
12. 独立批次页面不再作为业务入口，旧地址统一跳转翻拍工作台。

## 3. 范围与非目标

### 3.1 本次范围

- 团队范围的全局终端候选查询与终端搜索。
- 选择终端时自动创建或复用服务端隐藏快照。
- 同号实物免照片的直接翻拍状态。
- 终端级“一键替换全部无实物采集器”。
- 翻拍工作台界面和旧批次路由退役。
- 服务端权限、并发锁、审计、撤销、测试及发布验收。

### 3.2 非目标

- 不修改 `material_groups`、`photos` 或总清单中的原始编号、原始照片和分类。
- 不恢复采集器 Excel、照片目录或其他批量导入。
- 不跨项目共享、借用或调拨采集器池。
- 不自动登录、填写或上传甲方平台。
- 不改变表计和模块的新装照片规则。
- 不在本规范阶段执行生产部署、真实分配或真实甲方录入。

## 4. 总体架构

系统继续保留两个明确分离的入口：

### 4.1 手机采集器库存页

负责扫描手上实物，判断是否同号、是否需要拍照以及是否进入所属项目采集器池。

- 同号：保存实物确认，状态为 `direct`，`requires_photo=false`，不进入随机池。
- 非同号：先返回 `pool_needs_photo`；条码文本和一张有效照片原子提交成功后才保存为 `available`。
- 已经 `reserved` 或 `used` 的实物不能因重扫而回退状态。

新接口不再返回“同号仍需补拍”的 `direct_needs_photo` 决策。历史同号 `direct` 实物即使没有有效 `CollectorPhoto`，在打开终端时也按本规范协调为 `direct_ready`；历史照片保留但不再是同号直接翻拍的前置条件。非同号实物仍必须具有有效照片才能成为 `available`。

### 4.2 全局终端翻拍工作台

负责从当前团队施工数据中直接选择终端，展示新装照片、条码和拆旧采集器状态，并记录人工翻拍完成情况。

前端不显示项目选择器和批次选择器。服务端仍使用 `project_id` 限定数据和采集器池，并使用单终端隐藏运行保存不可变快照。对用户而言是“选择终端”；对后端而言仍是“团队 + 项目 + 终端快照”。

## 5. 全局终端候选与消歧

### 5.1 候选身份

终端候选的服务端身份是：

```text
team_id + project_id + normalize(terminal_code)
```

`normalize` 只去除首尾空白，不截断、不转数字、不丢前导零。同一项目内相同终端号的多个资料组属于同一个终端；不同项目中的相同终端号始终是两个不同候选，不能跨项目合并。

API 返回一个仅供前端回传的 `terminal_key`，同时返回内部 `project_id` 和完整 `terminal_code`。服务端不能信任前端回传的项目归属，打开终端时必须根据认证 `team_id` 重新验证项目和来源数据。

### 5.2 显示消歧

候选主标题固定显示终端号，副标题显示安装地址。出现以下情况时增加消歧信息：

- 同一团队多个项目存在相同终端号：显示项目名称和项目短编号。
- 同一项目同一终端号存在多个非空且不一致的安装地址：标记 `blocked`，列出地址冲突，不允许静默选择其中一个。
- 终端号为空：不进入默认候选列表，只计入管理员诊断。

同一项目内重复资料组不是冲突；它们按终端聚合，并按完整表号和完整采集器号分别生成电表项和去重采集器需求。

候选查询、隐藏快照和手机同号判断必须复用同一套来源投影规则：安装地址优先使用关联总清单行的权威值，缺失时才使用资料组快照；采集器号优先使用稳定排序后的首张有效照片 `collector`，没有非空照片值时再按现有兼容字段顺序读取资料组；模块号和两个新装照片槽位继续沿用当前 V3.2.8 的稳定选择规则。三处不得各自实现不同的编号优先级。

### 5.3 可选择状态

终端候选返回以下工作状态：

- `ready`：来源数据完整，全部去重采集器已有同号实物或已完成有效替换。
- `needs_replacement`：来源数据完整，存在无实物采集器，且所属项目可用池数量足够。
- `pool_shortage`：来源数据完整，但所属项目可用池数量少于无实物数量；允许打开查看，替换按钮禁用并显示缺口。
- `blocked`：终端号、表号、模块号、两张新装照片、采集器号或地址存在不可判定问题；默认不列入“可翻拍”结果，管理员可通过诊断筛选查看。

默认列表只返回前三类。查询必须分页，默认每页 50 条、最大 100 条，并使用选定列和数据库聚合完成，禁止加载整个项目的 `MaterialGroup`、`Photo` ORM 对象或构造项目级巨大 `IN (...)` 列表。

## 6. 隐藏终端快照

### 6.1 创建与复用

用户选择候选后，服务端只投影该项目、该终端的来源资料，并计算 `source_revision`。修订指纹由稳定排序后的以下语义字段计算：

- 项目和终端号；
- 安装地址；
- 每块表的资料组 ID、表号、模块号；
- 去重后的原采集器号；
- 两个新装槽位所选照片的记录 ID、SHA256 和存储标识。

时间戳、页面排序和无关 JSON 字段不参与指纹，避免无业务变化时误建快照。

服务端对 `team_id + project_id + terminal_code` 获取 PostgreSQL 事务级 advisory lock，然后：

1. 查找 `stats.workflow_kind=global_terminal_workbench` 且未被替代的最新隐藏运行。
2. 指纹相同则复用原运行和终端，返回 `snapshot_reused=true`。
3. 没有快照则创建只包含该终端的运行、电表项、采集器需求和工作项。每块表立即生成新装工作项；已确认同号实物的需求生成免照片拆旧工作项；无实物需求暂不生成拆旧工作项，但必须通过终端详情中的需求投影显示为“无实物”。
4. 所有隐藏元数据写入 `collector_transfer_runs.stats`，不新增用户可见批次。

隐藏运行名称只用于审计，例如 `全局翻拍/<终端号>/<修订短码>`；前端不得显示或要求用户选择该名称和 run ID。

### 6.2 来源数据变化策略

快照创建后保持不可变，来源数据变化不能静默覆盖已经翻拍或分配的记录。

- 指纹变化且旧快照没有已完成工作项、没有有效随机分配：在 `stats` 中把旧快照标记为 `superseded`，自动创建并返回新快照。
- 指纹变化且旧快照存在已完成工作项或有效随机分配：继续返回旧快照，并返回 `source_changed=true` 和差异摘要；不自动释放实物、不自动重分配。
- 管理员执行“刷新快照”前，必须先撤销全部完成状态并回滚全部随机分配。校验通过后旧快照标记为 `superseded`，再创建最新快照。
- 被替代快照保留审计和历史查询能力，但不再出现在默认终端列表，也不占用未完成的同号实物声明。

普通情况下用户看不到这套机制；只有施工来源在翻拍期间确实发生变化时，页面才显示提示和管理员处理入口。

## 7. 采集器状态与直接实物免照片

### 7.1 终端内展示状态

每个去重采集器需求只显示以下三种业务状态：

- `有实物`：存在当前项目同号 `PhysicalCollector`，并有成功的同号扫码确认；最终编号等于原编号。
- `无实物`：没有可绑定的同号实物，也没有有效随机分配。
- `已替换`：存在有效 `random` 分配；显示池内实物编号、条码和有效照片。

来源中同一采集器号如果异常出现在两个不同终端，不能同时声明同一实物。服务端锁定同号 `PhysicalCollector` 后查询未被替代快照中的直接工作项；已经被另一个终端声明时返回 `direct_conflict`，相关终端进入阻断诊断，等待人工核对来源数据。

打开或重新读取终端时，服务端对仍为 `unmatched` 且没有有效随机分配的需求执行一次幂等直接实物协调：按统一锁顺序查找当前项目同号 `direct` 实物，检查跨终端声明冲突，然后创建免照片工作项并把需求改为 `direct_ready`。如果需求已经有随机分配，后来发生的同号扫码不能静默替换持久化随机结果；管理员必须先回滚随机分配，再由下一次读取完成直接绑定。

### 7.2 不使用假照片、不新增直接分配照片

现有 `CollectorAssignment.collector_photo_id` 非空，因此免照片的同号实物不创建伪造 `CollectorPhoto`，也不创建缺照片的 `CollectorAssignment`。

同号实物使用现有可空关联表达：

- `CollectorRequirement.status = direct_ready`；
- 创建 `CollectorWorkbenchItem(item_kind=collector_removal, requirement_id=<需求>, assignment_id=NULL)`；
- `PhysicalCollector.pool_status` 在待翻拍时保持 `direct`；
- 工作台通过 `run.project_id + requirement.original_collector_no` 重新解析并锁定唯一实物。

直接实物拆旧项的 DTO 明确返回 `capture_strategy=live_physical`、`photo=null`。前端显示“请直接对准手上实物翻拍”，完成校验不得要求网站照片。

### 7.3 直接实物完成与撤销

直接实物项标记完成时，在一个事务中锁定运行、终端、需求、实物和工作项：

- 工作项 `pending -> completed`；
- 需求 `direct_ready -> used`；
- 实物 `direct -> used`；
- 保存完成操作者和时间并写审计。

撤销完成时执行反向状态：

- 工作项 `completed -> pending`；
- 需求 `used -> direct_ready`；
- 实物 `used -> direct`；
- 写入撤销操作者、原完成信息和时间。

这类撤销只是撤销翻拍完成，不会把同号实物加入随机池。

## 8. 终端级原子随机替换

### 8.1 操作范围

“一键替换全部无实物采集器”只处理当前终端中：

- 状态为 `unmatched`；
- 没有有效直接实物工作项；
- 没有 `reserved` 或 `used` 分配；
- 没有来源诊断阻断的需求。

已经“有实物”或“已替换”的采集器不参与抽取。重复点击时若缺口为零，返回幂等成功，不创建新分配。

### 8.2 事务和锁顺序

替换、回滚和完成操作统一采用以下数据库锁顺序：

```text
run -> terminal -> requirements(sorted id) -> physical_collectors(sorted id)
    -> assignments(sorted id) -> workbench_items(sorted id)
```

实现时需要把现有涉及同一批表的回滚和完成路径调整到同一顺序，避免新旧入口交叉死锁。

替换事务执行：

1. 重新验证认证团队、隐藏运行、终端和项目归属。
2. 锁定运行、终端及全部当前缺口需求，并重新计算 `required`。
3. 查询并按 ID 锁定同团队、同项目、状态为 `available`、具有唯一有效照片且没有有效分配的实物。
4. 锁完成后重新计算 `available`。若 `available < required`，返回 `409 pool_insufficient`；本事务不写分配、状态或工作项。
5. 调用现有 `plan_random_assignments`，从已锁定候选中一次抽取等量且互不重复的实物。
6. 为每个需求创建 `random` 分配，绑定有效照片；需求改为 `assigned`，实物改为 `reserved`，创建拆旧工作项。
7. 写入批量审计和逐条映射后一次提交。

数据库现有局部唯一索引继续兜底：一个有效需求只能有一个有效分配，一个实物只能出现在一个有效分配中。任何唯一约束竞争、照片失效或状态变化都使整笔事务回滚并返回稳定冲突码。

### 8.3 随机项完成、撤销与回滚

- 标记完成：分配 `reserved -> used`、需求 `assigned -> used`、实物 `reserved -> used`、工作项完成。
- 撤销完成：分配 `used -> reserved`、需求 `used -> assigned`、实物 `used -> reserved`、工作项恢复待完成。
- 管理员回滚分配：分配改为 `rolled_back`，需求恢复 `unmatched`，实物恢复 `available`，对应拆旧工作项删除；原分配和审计保留。
- 回滚后终端重新显示“无实物”，可以再次执行终端级一键替换。

同号直接实物没有随机分配，因此不显示“回滚替换”；它只支持完成/撤销完成。

## 9. API 与 DTO 合同

### 9.1 全局终端列表

`GET /collector-transfer/workbench/terminals`

查询参数：

- `query`：终端号或地址文本；
- `state`：`ready | needs_replacement | pool_shortage | blocked`；
- `page`、`page_size`；
- `include_blocked`：仅管理员可用。

核心响应：

```json
{
  "items": [
    {
      "terminal_key": "opaque-key",
      "project_id": "uuid",
      "project_name": "项目名称",
      "terminal_code": "000123",
      "installation_address": "安装地址",
      "needs_disambiguation": false,
      "meter_count": 4,
      "collector_count": 2,
      "physical_count": 1,
      "missing_count": 1,
      "pool_available_count": 7,
      "workflow_state": "needs_replacement",
      "selectable": true,
      "source_revision": "sha256",
      "diagnostics": []
    }
  ],
  "page": 1,
  "page_size": 50,
  "total": 1
}
```

`project_id` 是后端隔离所需的内部字段，不等于前端恢复项目选择器。页面只在需要消歧时显示项目信息。

### 9.2 打开或复用终端

`POST /collector-transfer/workbench/terminals/open`

请求：

```json
{
  "terminal_key": "opaque-key",
  "project_id": "uuid",
  "terminal_code": "000123",
  "source_revision": "list-response-sha256"
}
```

响应返回 `workbench_terminal_id`、是否复用、是否来源变化、终端汇总和当前工作项。服务端始终重新鉴权并重算来源，不以 `terminal_key`、`project_id` 或旧 `source_revision` 作为授权依据。

### 9.3 终端详情

`GET /collector-transfer/workbench/terminals/{workbench_terminal_id}`

终端详情包含：

- `meter_install_items`：表号、模块号、两个 Code 128 值和两张来源照片；
- `collector_items`：原采集器号、`physical_state`、最终采集器号、条码、照片、`capture_strategy`、分配 ID和可执行动作；
- 终端完成数、缺口数、可用池数量、诊断和来源变化提示。

采集器 DTO 约束：

```text
present  -> final_collector_no=original, capture_strategy=live_physical, photo=null
missing  -> final_collector_no=null,     capture_strategy=unavailable,   photo=null
replaced -> final_collector_no=pool no,  capture_strategy=screen_photo,  photo=active pool photo
```

### 9.4 终端内替换与刷新

- `POST /collector-transfer/workbench/terminals/{workbench_terminal_id}/replace-missing`：管理员一键替换全部当前缺口。
- `POST /collector-transfer/workbench/terminals/{workbench_terminal_id}/refresh`：管理员在满足无进度、无有效分配条件后重建来源快照。
- `POST /collector-transfer/assignments/{assignment_id}/rollback`：管理员回滚单条随机替换。
- `PATCH /collector-transfer/workbench/items/{item_id}`：管理员或施工员标记完成或撤销完成。

原 `POST /collector-transfer/runs/{run_id}/allocate` 和批次查询接口在本次 V3.2.8 实现中保留，但改为服务端管理员权限，新页面不再调用；隐藏运行不得通过旧接口绕过终端级校验。是否在后续版本物理删除必须另行评审。

### 9.5 稳定错误码

- `terminal_not_found`：团队范围内找不到候选或快照；
- `terminal_source_blocked`：来源资料不满足新装或拆旧合同；
- `snapshot_changed`：管理员请求刷新或调用方要求最新快照，但旧快照存在未撤销进度；普通打开操作仍返回旧快照和 `source_changed=true`；
- `direct_conflict`：同号实物已被另一终端有效声明；
- `pool_insufficient`：池数量不足，返回 `required`、`available`、`shortage`；
- `allocation_conflict`：并发或约束竞争导致整笔替换回滚；
- `workbench_incomplete`：完成动作缺少必要条码、来源照片或随机替换照片；
- `forbidden`：非管理员尝试替换、回滚、刷新或调用旧分配接口。

## 10. 服务端权限与隔离

认证 token 是团队、操作者和角色的唯一可信来源。请求体、查询参数和前端本地存储中的团队、操作者、角色都不可信。

权限矩阵：

| 操作 | 管理员 | 施工员 |
| --- | --- | --- |
| 手机扫码、同号确认、非同号拍照入池 | 允许 | 允许 |
| 搜索、打开、查看终端翻拍工作台 | 允许 | 允许 |
| 标记翻拍完成、撤销完成 | 允许 | 允许 |
| 一键替换无实物采集器 | 允许 | 禁止 |
| 回滚随机替换 | 允许 | 禁止 |
| 刷新已有进度的终端快照 | 允许 | 禁止 |
| 旧批次分配接口 | 兼容期允许 | 禁止 |

路由层必须从认证上下文取得 `team_id`、用户名和角色，服务层再次验证项目、运行、终端、需求、实物、照片和分配属于同一团队及同一项目。前端隐藏按钮只是交互优化，不能代替服务端 `403`。

## 11. 翻拍工作台界面

### 11.1 顶部终端选择

移除现有“项目、批次、终端”三级选择，改为：

- 一个可搜索的“选择可翻拍终端”输入框；
- 候选行显示终端号、地址、表数、采集器数和状态；
- 只有重号时补充项目名称和项目短编号；
- 状态明确显示“可直接翻拍、需替换 N 个、池不足 N 个”。

选择终端后自动打开或复用隐藏快照，不出现“创建批次”步骤。

### 11.2 终端内容

新装区保持现有两槽位：

- 表号 Code 128；
- 模块号 Code 128；
- “电表和模块”照片；
- “改造完成”照片。

拆旧区按去重采集器显示卡片：

- `有实物`：原号条码，绿色状态，提示直接拿实物翻拍，不显示缺图错误。
- `无实物`：原号和缺口状态，不生成可供甲方录入的最终条码。
- `已替换`：原号作为审计参考，突出显示替换后号码、Code 128 和池内照片。

管理员在终端汇总区域看到“一键替换全部 N 个无实物采集器”。施工员只能看到状态，不显示可操作的替换按钮。池不足时按钮禁用，旁边显示“需要 N / 可用 M”。

### 11.3 完成操作

保留上一项、下一项、标记已翻拍和撤销完成。完成校验按类型区分：

- 新装项必须有表号、模块号和两张来源照片；
- 同号直接实物项必须有采集器号和有效扫码实物绑定，不要求网站照片；
- 随机替换项必须有替换后编号和有效池内照片；
- 无实物项不能标记完成。

工作台不调用手机摄像头、不拍摄现场照片，也不包含甲方平台账号或表单。手机摄像头能力只属于采集器库存扫码页。

## 12. 页面与路由退役

- 从 `staticPages` 和顶部导航移除 `collector-batches`。

## 13. 并发、幂等与失败恢复

- 相同终端并发打开通过 advisory lock 只创建一个同修订隐藏快照，其余请求复用。
- 相同终端并发替换时，只有一个事务能持有运行、需求和池行锁；后到请求返回幂等成功或受控冲突。
- 不同终端并发抽取同一项目池时，按实物 ID 排序锁定，数据库唯一索引保证实物不被重复消费。
- 池不足、照片在锁后失效、项目不一致或唯一约束竞争均不得留下部分分配。
- 页面请求切换终端时使用请求序号或 `AbortController`；迟到响应不得覆盖当前终端。
- 写请求完成后前端重新读取终端详情，以服务端持久化状态为准，不在本地猜测随机结果。
- 任一失败响应必须保留当前页面和可重试入口，不得显示“已替换”或“已完成”的乐观假状态。

- `collector_workbench.snapshot_superseded`；

## 15. 数据库与迁移决策

本设计优先复用现有字段，不新增 Alembic migration：

- 隐藏工作流和来源修订保存在 `CollectorTransferRun.stats`；
- 同号需求使用现有 `direct_ready`、`used`；
- 同号实物使用现有 `direct`、`used`；
- 免照片拆旧项使用 `CollectorWorkbenchItem.requirement_id` 和可空 `assignment_id`；
- 随机替换继续使用现有 `CollectorAssignment` 和非空 `collector_photo_id`。

因此数据库 head 保持 `20260824_0016`。如果实现阶段证明现有约束无法安全表达本规范中的直接实物唯一声明，必须暂停并升级设计，不能以假照片、放宽照片非空约束或无审计 JSON 临时拼接绕过。

## 16. 测试计划与验收标准

### 16.1 领域和服务测试

- 一个终端多表共享一个采集器只生成一个拆旧需求。
- 不同项目相同终端号生成两个候选，并显示消歧信息。
- 同一项目同终端号地址冲突进入 `blocked`。
- 同号扫码直接返回无需拍照，保存 `direct`，不创建 `CollectorPhoto`，不进入随机池。
- 免照片直接实物能生成拆旧工作项、完成和撤销完成。
- 同一直接实物不能被两个不同终端有效声明。
- 指纹相同复用隐藏快照；无进度变更自动替代；有进度变更不静默覆盖。
- 终端级替换只处理当前全部缺口，重复点击幂等。
- 池不足时分配、需求、实物、工作项和完成状态均零变化。
- 随机分配完成、撤销完成和管理员回滚状态正确。

### 16.2 PostgreSQL 并发测试

- 相同终端并发打开只产生一个当前修订快照。
- 两个终端并发替换不重复使用采集器或照片。
- 替换与回滚、替换与完成并发遵循统一锁顺序且不死锁。
- 数据库局部唯一索引在竞争时使整笔请求回滚。
- 项目 A 的池绝不进入项目 B 的终端；跨团队请求稳定返回不可见或禁止。

### 16.3 API 权限测试

- 管理员可替换、回滚、刷新。
- 施工员调用上述接口返回 `403 forbidden` 且零业务副作用。
- 管理员和施工员可查看并完成工作项。
- 请求伪造 `team_id`、`project_id`、actor 或角色不能越权。
- 旧 `/runs/{run_id}/allocate` 不能被施工员调用，也不能用于绕过隐藏终端校验。

### 16.4 前端测试

- 工作台没有项目选择、批次选择和创建批次入口。
- 终端搜索、重号消歧、池不足、来源变化和空结果文案明确。
- 三种采集器状态与可执行动作准确。
- 同号实物不因 `photo=null` 被判定为缺图或禁止完成。
- 施工员看不到替换按钮；即使手工发请求也由服务端拒绝。
- `/collector-batches` 跳转 `/collector-workbench`，导航中不再出现批次页面。
- 迟到响应不会覆盖新选中的终端。

### 16.5 发布与生产验收

1. 全量后端、前端组件、类型检查、Vue 生产构建和发布包校验全部通过。
2. 发布包必须从最终源码提交重新构建，并通过源码字节绑定、Vue 清单哈希和 ZIP CRC 校验，不能复用旧候选包。
3. 生产切换前创建并验证一份可恢复的流式备份；不清理现有 release 或 backup。
4. 切换后不仅检查 systemd `active`，还必须等待 `127.0.0.1:8000` 的真实 Uvicorn listener。
5. 只使用受控测试终端验证：全局终端可见、同号显示有实物、池不足零分配、管理员一键替换和回滚。
6. 使用真实手机验证采集器库存扫码相机权限、预览、连续扫码和退出清理；浏览器网络记录不得出现甲方平台请求。
7. 验收通过后再恢复维护 worker/timer；失败时按已验证备份和上一 release 整体回滚。

生产发布、真实终端替换和真实甲方平台翻拍仍需用户在实现及本地验收完成后另行确认。
