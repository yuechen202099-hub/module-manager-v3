# 项目级无批次采集器扫码入池设计

## 1. 背景与目标

V3.2.6 已有采集器中转、随机一次性分配和手机翻拍工作台，但手机采集器盘点仍依赖 `collector_transfer_runs`。本次调整把“手上实物采集器的登记”从批次生命周期中拆出，形成当前项目独立的长期库存。

目标流程是：手机打开采集器页面后直接扫描条形码文本；同号实物按项目需求直接确认，非同号实物在条码和一张照片同时成功提交后进入随机替换池。批次只负责终端需求快照、一次性分配和翻拍工作台。

本次继续遵守以下边界：

- 不修改 `material_groups`、`photos` 中的原始施工编号和照片。
- 不提供采集器 Excel、照片或其他批量导入功能。
- 扫码和拍照不录入、不登录、不调用、不自动上传甲方平台。
- 新装仍只有“电表和模块”与“改造完成”两个照片槽位；拆旧采集器仍只有一个照片槽位。

## 2. 已确认业务规则

1. 采集器库存以当前项目为边界，不在同一团队的不同项目之间共享。
2. 手机页面自动使用工作区当前项目，不显示批次选择、批次创建或“无批次不能扫码”的空状态。
3. 条码按文本保存，只去除首尾空白，不限制为纯数字，不截断前导零。
4. 同号是指扫码文本与当前项目现有施工资料投影出的待拆采集器号完全相同。
5. 同号且已有当前有效实物照片时，保存“同号已确认”并直接用于后续同号翻拍，不重新拍照、不进入随机池。
6. 同号但没有当前有效实物照片时允许逐个拍照；照片成功后状态为 `direct`，仍不进入随机池。
7. 非同号扫码只返回“需要拍照”，不创建采集器、照片、待拍草稿或业务扫码事件。
8. 非同号只有在条码文本和照片同时提交、全部校验成功后才创建库存记录，状态直接为 `available`。
9. 用户取消拍照、关闭页面或照片上传失败时，不在服务器留下非同号待拍记录。
10. 同一项目内采集器号和照片内容禁止重复登记；不同项目允许出现相同编号或相同照片。
11. 随机池仍按 `available -> reserved -> used` 一次性消耗，禁止重复分配和重复使用。
12. 一个终端的拆旧需求仍按该终端内采集器号去重；一台采集器关联多块电表时只生成一个拆旧项。

## 3. 架构边界

系统拆成两个生命周期：

### 3.1 项目采集器库存

项目库存长期存在，与任何运行批次无关，负责：

- 使用当前项目施工资料判断同号或非同号。
- 保存同号实物确认。
- 原子登记“条码文本 + 一张实物照片”。
- 提供项目内去重、状态查询、照片替换和审计。

`physical_collectors` 是实物台账，不等同于随机池。只有状态为 `available` 的非同号实物才属于随机池；状态为 `direct` 的同号实物只允许同号匹配。

### 3.2 分配运行与翻拍工作台

`collector_transfer_runs` 继续负责：

- 从当前项目现有数据生成终端、电表和去重后的采集器需求快照。
- 优先使用项目库存中的同号实物完成 `direct` 分配。
- 从当前项目 `available` 池中随机选择剩余需求数量，执行一次性 `random` 分配。
- 生成并维护手机翻拍工作项。

运行不再拥有或创建采集器库存。运行只能消费与 `run.project_id` 相同的库存。

## 4. 数据模型调整

### 4.1 `physical_collectors`

- 新增非空 `project_id`，外键指向 `projects.id`。
- 唯一约束由 `(team_id, collector_no)` 改为 `(team_id, project_id, collector_no)`。
- 增加项目状态查询索引 `(team_id, project_id, pool_status)`。
- `first_seen_run_id` 只作为旧数据来源和审计兼容字段，不再是新库存登记的前置条件。
- `last_scanned_at`、操作者和审计记录用于证明同号实物已确认在手。
- 新流程使用 `direct`、`available`、`reserved`、`used`；历史 `awaiting_photo` 只作为不可分配的遗留状态保留，新接口不得创建它。
- `direct` 是否仍需照片通过是否存在当前有效 `collector_photos` 记录判断，不另建随机池记录。

### 4.2 `collector_photos`

- 新增非空 `project_id`，必须与所属 `physical_collector.project_id` 一致。
- SHA256 唯一约束由 `(team_id, sha256)` 改为 `(team_id, project_id, sha256)`。
- 使用局部唯一索引保证同一实物最多只有一张 `is_active=true` 的照片；显式重新拍照时先保存新照片，事务提交时停用旧照片，旧文件和记录保留用于审计。
- 普通重复提交不得静默替换照片；只有页面明确选择“重新拍照”时才允许更换当前有效照片。

### 4.3 `collector_scan_events`

- 新增非空 `project_id`。
- `run_id` 改为可空；项目库存扫码不再要求运行批次。
- 同号确认、成功的照片登记、重复库存命中和已使用阻断可以写业务事件。
- 非同号初次扫码后取消或失败不得写业务扫码事件；这类请求只保留常规服务访问日志。

### 4.4 运行侧表

- `collector_requirements`、`collector_assignments` 和 `collector_workbench_items` 继续属于运行。
- 创建 `direct` 或 `random` 分配前必须验证实物、照片、需求和运行属于同一团队及同一项目。
- 数据库继续保证一个有效需求只有一个有效分配、一个实物只有一个 `reserved` 或 `used` 分配。
- 回滚 `direct` 分配后实物仍为 `direct`，不得降级进入随机池；回滚 `random` 分配后才可恢复为 `available`。

## 5. 项目同号来源

无批次扫码不能依赖 `collector_requirements`，因此同号判断直接复用运行生成时的项目投影规则：

1. 只读取当前项目的 `material_groups` 与有效 `photos`。
2. 原采集器号优先读取有效照片中的 `collector`，再读取资料组兼容字段。
3. 按去首尾空白后的完整文本比较，不使用电表长短码匹配。
4. 结果仅用于判断当前项目是否存在该待拆编号，不修改来源数据。

运行创建与库存扫码必须调用同一个投影函数，防止“扫码认为同号、运行生成却认为非同号”的规则漂移。

## 6. API 契约

### 6.1 项目库存扫码

`POST /collector-transfer/inventory/scan`

请求：

- `project_id`
- `collector_no`

服务端从认证信息取得 `team_id` 和操作者，并验证项目属于该团队且处于可用状态。响应决策包括：

- `direct_reuse`：同号且已有有效照片；幂等保存同号确认，不要求拍照。
- `direct_needs_photo`：同号但没有有效照片；保存 `direct` 实物确认并要求拍照。
- `pool_needs_photo`：非同号且未登记；不写业务数据，只要求拍照。
- `existing_available`：已在当前项目随机池中；不重复拍照或创建。
- `existing_reserved`：已分配；禁止重复操作。
- `existing_used`：已使用；禁止重复操作。

### 6.2 条码和照片原子登记

`POST /collector-transfer/inventory`

使用 `multipart/form-data` 一次提交：

- `project_id`
- `collector_no`
- `file`

服务端在写入前重新判断同号状态，不能信任上一次扫码响应。照片完成格式、大小、可解码性和 SHA256 校验后：

- 同号创建或更新 `direct` 实物及有效照片。
- 非同号在同一数据库事务内创建 `available` 实物、有效照片和审计记录。
- 相同 SHA256 已绑定同一实物时按幂等成功返回。
- 相同 SHA256 已绑定当前项目另一实物时返回 `409 photo_conflict`。
- 文件已保存但数据库事务失败时清理本次新建的孤立存储对象。

虽然文件存储与 PostgreSQL 不能形成物理上的同一事务，对调用方必须表现为原子操作：只有数据库提交完成才返回入池成功；失败路径不得留下可用库存或未引用新文件。

### 6.3 查询与照片替换

- `GET /collector-transfer/inventory?project_id=...`：返回项目库存统计、最近登记和状态筛选结果。
- `POST /collector-transfer/inventory/{collector_id}/photo`：只用于已登记实物的显式补拍或重新拍照；替换时要求明确标志并保留旧记录。

现有 `/collector-transfer/runs/{run_id}/scan` 与 `/collector-transfer/runs/{run_id}/collectors/{collector_id}/photo` 不再由前端调用，并在切换后退役，防止继续创建批次绑定的 `awaiting_photo` 数据。批次创建、查询、分配、回滚和工作台接口继续保留。

## 7. 手机页面

`CollectorInventoryView.vue` 调整为单一项目库存页面：

1. 页面打开后读取工作区当前项目和最近库存记录。
2. 顶部醒目显示项目名称与项目编号，不显示运行批次。
3. 主操作区默认提供摄像头扫码；不支持摄像头时保留手工输入和外接扫码枪。
4. `direct_reuse` 显示“同号已确认，可直接翻拍”和当前有效照片预览。
5. `direct_needs_photo` 与 `pool_needs_photo` 进入手机拍照、预览、确认流程。
6. 照片提交成功后分别显示“同号照片已保存，不进入随机池”或“已进入当前项目采集器池”。
7. 取消拍照不调用登记接口；上传失败时只在当前页面内保留条码和本地预览供重试，刷新或关闭后丢弃。
8. 请求过程中切换项目时，旧响应不得写入新项目页面；服务端也必须按请求中的项目重新鉴权。
9. 页面保留“仅做盘点与补拍，不录入甲方平台”的明确提示。

如果工作区没有当前项目，页面只能提示先选择项目；不得猜测项目或自动使用最近一次项目。

## 8. 分配与翻拍数据流

创建运行后，服务按当前项目读取库存：

1. 对每个去重采集器需求查找未被消耗的同号实物。
2. 同号实物有有效照片时创建 `direct` 分配和拆旧翻拍项。
3. 同号实物缺少有效照片时，需求保持 `direct_pending_photo`，随机分配不得绕过该同号确认。
4. 其余未匹配需求只从当前项目的 `available` 实物中随机分配。
5. 池数量不足时整笔失败，不允许部分分配。
6. 分配、刷新、并发请求和服务重启都不得改变已持久化结果。
7. 工作台继续显示每块电表的两个新装照片槽位，以及每个去重采集器的一张拆旧照片和条码文本。

## 9. 重复、并发与错误处理

- 空条码、无权限项目、停用项目、无效图片和不可解码图片在任何业务写入前拒绝。
- 当前项目相同编号重复扫码返回现有状态，不创建第二条实物记录。
- `reserved` 或 `used` 实物不得因重扫、重复上传或照片替换退回 `direct` 或 `available`。
- 并发登记相同编号时由项目级唯一约束决定唯一胜者，失败请求读取胜者并返回幂等结果。
- 并发提交相同照片到不同编号时只允许一个成功，另一个稳定返回冲突。
- 并发分配继续按运行、需求、实物、分配、工作项的统一锁顺序执行。
- 所有错误响应使用稳定业务码，手机页面不得把失败显示为已入池。
- 项目 A 的编号、照片、统计和分配不得出现在项目 B；不同项目的相同编号和 SHA256 合法共存。

## 10. 数据迁移与发布边界

新增 Alembic 迁移接在现有 `20260823_0015` 之后。迁移步骤：

1. 先给 `physical_collectors`、`collector_photos`、`collector_scan_events` 增加可空 `project_id`。
2. `physical_collectors.project_id` 优先从 `first_seen_run_id -> collector_transfer_runs.project_id` 回填，并用历史扫描事件与分配关系交叉校验。
3. `collector_photos.project_id` 从所属实物回填；扫描事件从所属运行或实物回填。
4. 预检同一实物是否跨项目出现在运行、扫描或分配关系中。存在歧义时迁移立即失败并输出记录 ID，不猜测归属。
5. 回填完整并通过一致性查询后设为非空，替换团队级唯一约束并增加项目索引。
6. 历史 `awaiting_photo` 不自动删除、不自动入池；保持不可分配并列入迁移报告，后续只能逐条确认处理。

项目级唯一约束上线后，同一团队可在不同项目创建相同编号，这会破坏旧版本的团队级唯一假设。因此生产切换前必须完成数据库与上传目录备份；一旦新版本产生跨项目重复编号，应用回退必须同时恢复切换前数据库和对应文件备份，不能只切换旧代码目录。

本设计文档和后续本地实现不自动授权生产迁移、真实扫码、真实分配或甲方平台操作。生产发布需要在完整测试和发布包校验后另行确认。

## 11. 测试与验收

### 11.1 后端领域与 API

- 无 `run_id` 时可完成项目库存扫码与照片登记。
- 同号有图返回 `direct_reuse`，同号无图返回 `direct_needs_photo`，两者都不进入随机池。
- 非同号扫码后取消、上传失败或关闭页面时，实物、照片和业务扫码事件均为零新增。
- 非同号条码与有效照片成功提交后直接产生一条 `available` 实物和一张有效照片。
- 同一项目的编号与 SHA256 正确幂等或冲突；不同项目允许相同值。
- 团队越权、项目越权和停用项目请求稳定失败且零副作用。

### 11.2 PostgreSQL 集成

- 项目级唯一约束能处理相同编号并发登记。
- 相同照片并发绑定不同实物时只有一个提交成功。
- 一个实物或需求不会被两个运行同时 `reserved` 或 `used`。
- 项目不一致的运行、实物、照片和需求不能形成分配。
- 迁移回填、歧义阻断、索引和约束 DDL 均有测试。

### 11.3 前端

- 页面没有批次选择、批次创建、批量导入和甲方平台录入入口。
- 摄像头扫码、手工输入、拍照预览、取消、失败重试和连续扫码均可用。
- 同号确认、同号补拍、随机池补拍、已分配和已使用状态文案明确。
- 当前项目名称始终可见；切换项目不会混入旧响应或旧列表。
- 在 390px 手机宽度无横向溢出，桌面访问仍可正确显示但不增加批次操作。

### 11.4 回归与生产验收

- 终端内多表共享采集器时只生成一个拆旧需求。
- 批次需求生成、直接匹配、随机分配、回滚和翻拍工作台全部通过。
- 池不足整笔失败，并发分配不重复消耗。
- 新装严格为两张照片，拆旧严格为一张照片。
- 使用两个测试项目验证相同编号和相同照片彼此隔离。
- 浏览器网络记录证明扫码和拍照未调用任何甲方平台接口。

## 12. 非目标

- 不自动登录、填写或上传甲方平台。
- 不恢复任何采集器批量导入能力。
- 不修改原始施工数据或用新照片覆盖 `photos`。
- 不改变表计和模块的新装照片规则。
- 不跨项目共享、借用或调拨采集器库存。
