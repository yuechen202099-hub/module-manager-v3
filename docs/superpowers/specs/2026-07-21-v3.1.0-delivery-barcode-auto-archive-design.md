# V3.1.0 交付导出、条码核验与自动归档设计

## 1. 版本范围

`V3.1.0` 基于完成发布的 `V3.0.84` 开发，包含以下业务升级：

1. 新旧设备双 Sheet 交付清单。
2. 新的照片目录与文件命名规则。
3. 施工上传槽位成为正式照片分类来源。
4. 条码、二维码、OCR 与人工确认的资料组级核验。
5. 条码通过后的自动归档。
6. 历史分类回填与低负载后台扫描维护。

本版本不改变施工工单匹配、`00000000` 拦截、KPI、登录有效期、任务领取和审阅权限规则。

## 2. 交付工作簿

交付包根目录生成 `设备清单.xlsx`，包含两个 Sheet，所有设备标识字段按文本写入，禁止科学计数法、前导零丢失和 `00000000` 等占位值。

### 2.1 老设备

列顺序和来源：

| 列名 | 来源 |
| --- | --- |
| 终端地址 | 系统终端号 |
| 终端厂家 | 空 |
| 终端安装地址 | 系统安装地址 |
| 表号 | 系统表号 |
| 采集器设备号 | 填报或人工确认后的采集器号 |
| 供服中心 | 固定 `南大供电服务中心` |
| 改造工程队 | 固定 `奕福` |
| 旧设备拆除时间 | 空 |
| 旧设备状态 | 空 |

### 2.2 新设备

列顺序和来源：

| 列名 | 来源 |
| --- | --- |
| 改造日期 | 施工端 `client_completed_at`，按本地日期输出 |
| 模块对应的表号 | 系统表号 |
| 新模块编号 | 填报或人工确认后的模块号 |
| 备注 | 异常、人工确认等必要说明；正常为空 |

当前正式规则以已确认列名和顺序生成系统工作簿，不依赖未提供的原始 Excel 模板。后续收到上级原始模板时，仅做模板样式适配，不改变本设计的数据映射。

### 2.3 导出范围与校验

- 默认只导出已归档资料组。
- 终端号、表号或模块号缺失时，禁止进入正式交付包，并返回可导出的错误清单。
- `client_completed_at` 缺失或无法解析为有效日期时，禁止导出新设备记录。
- 正式导出要求恰好四张有效照片且四个分类唯一完整。
- 采集器号缺失时禁止导出老设备记录。
- 同一资料组在两个 Sheet 中各最多一行。
- 导出过程按资料组 ID 去重；设备号相同但资料组不同的冲突进入错误清单，不静默覆盖。

## 3. 照片交付结构

交付 ZIP 结构固定为：

```text
设备清单.xlsx
终端号/
  表号-模块号-安装地址/
    模块号-表箱整体改造前.jpg
    模块号-采集器条形码.jpg
    模块号-模块与电能表.jpg
    模块号-表箱整体改造后.jpg
```

规则：

- 保留原始图片扩展名，不强制转码。
- Windows 非法路径字符、控制字符和结尾空格或点替换为 `_`。
- 同名冲突使用稳定资料组 ID 后缀解决，不覆盖文件。
- 终端号、表号、模块号或安装地址缺失时阻止正式导出。
- 只导出当前有效照片，不导出已删除、已撤销或历史版本照片。
- 照片分类必须对应四个标准分类，不允许 `unclassified`、重复分类或额外第五张有效照片进入正式包。

## 4. 照片分类来源

### 4.1 权威分类

施工端四个上传槽位是照片分类的第一权威来源：

- `before_box`：表箱整体改造前。
- `collector_barcode`：采集器条形码。
- `module_meter`：模块与电能表。
- `after_box`：表箱整体改造后。

上传成功时服务端保存 `construction_slot` 并同步写入标准 `category`。服务端必须校验四个槽位唯一且完整，不能相信前端自由文本。

### 4.2 审阅纠正

- 审阅工作台不再要求重复完成四张照片分类。
- 分类控件保留为“纠正分类”，只在施工端分类错误时使用。
- 每次纠正分类写入审计日志，记录资料组、照片、旧分类、新分类、操作人和时间。
- 修改分类属于证据变化，必须使旧条码核验结果失效并重新排队。

### 4.3 历史回填

- 对 `category=unclassified` 且存在合法 `construction_slot` 的历史有效照片回填标准分类。
- 已存在人工分类的照片绝不覆盖。
- 回填前后数量、冲突、跳过和失败记录写入维护报告。
- 历史已归档资料组不批量回退；其分类只在明确需要重新交付时校验。

## 5. 条码核验资格

只有同时满足以下条件的资料组才进入自动扫描：

1. 恰好四张有效照片。
2. 四张照片分别对应四个唯一标准分类。
3. 资料组具有真实终端号和表号。
4. 已填报真实模块号和采集器号。
5. 不存在 `00000000`、全零、测试值或其他占位标识。

不满四张、超过四张、分类重复、分类缺失或身份字段缺失的资料组不执行条码扫描，状态标记为“不具备扫描条件”，不得混入“无法识别”。

## 6. 资料组级识别规则

### 6.1 期望值

每个资料组有三个期望值：

- 表号。
- 模块号。
- 采集器号。

### 6.2 识别来源

后台依次使用：

1. 一维条码识别。
2. 二维码识别。
3. OCR 候选识别。

图像预处理可以包含方向检测、多个旋转角度、透视校正、局部增强、灰度、对比度、锐化、二值化和多尺度识别。处理必须有单图时间与内存上限，禁止并行拉满服务器 CPU。

### 6.3 通过口径

- 在四张照片的全部机器识别结果中，只要三个期望值分别至少出现一次，即资料组机器核验为 `3/3`。
- 三个值不要求出现在固定照片，也不要求每张照片都识别成功。
- 照片中出现额外无关条码或二维码不导致资料组失败。
- 机器直接读取的一维条码和二维码可作为正式匹配证据。
- OCR 结果只能作为候选，未经人工确认不能自动写入正式字段，也不能单独触发自动归档。
- 人工框选识别结果必须由人工选择类型并二次确认，确认后才能写入表号、模块号或采集器号。

### 6.4 状态

资料组核验状态包括：

- `not_eligible`：不具备扫描条件。
- `pending`：等待后台扫描。
- `processing`：正在扫描。
- `passed`：机器条码或二维码 `3/3`。
- `partial`：匹配 `1/3` 或 `2/3`。
- `unreadable`：四张照片完成识别但没有形成有效候选。
- `mismatch`：识别到明确值但与填报值不一致。
- `manual_confirmed`：人工确认三个值完整并认可证据。
- `failed`：技术失败，可重试。

前端显示统一进度标签 `0/3`、`1/3`、`2/3`、`3/3`，并区分机器通过和人工确认。

## 7. 结果失效与人工确认

以下任一变化使旧核验结果失效并重新进入 `pending`：

- 新增、删除、恢复或替换照片。
- 修改照片分类。
- 修改表号、模块号或采集器号。
- 将资料组回退至未施工或未审阅。

失效时保留历史结果和审计记录，但清除当前有效的通过标志。人工确认不能阻止后续证据变化导致失效。

人工确认必须记录：

- 确认前的三个期望值和识别结果。
- 确认后的三个正式值。
- 操作人、时间、原因和相关照片 ID。
- 被人工覆盖的异常或无法识别状态。

人工确认后当前资料组不得继续计入异常或无法识别，驾驶舱准确率和列表统计必须使用最新有效结果。

## 8. 自动归档

满足以下任一条件时自动归档：

1. 四张照片分类完整且机器条码或二维码核验 `3/3`。
2. 四张照片分类完整且人工确认状态为 `manual_confirmed`，三个正式值完整。

自动归档必须：

- 在数据库事务中再次校验照片、分类、身份字段和核验结果。
- 使用行锁或等效锁避免两个工作进程重复归档。
- 具备幂等性，重复执行不产生重复审计或重复文件。
- 写入归档来源 `machine_barcode`、`machine_qr` 或 `manual_confirmed`。
- 写入归档时间、核验版本和审计事件。

分类完整但只有 OCR 候选、`partial`、`unreadable`、`mismatch` 或 `failed` 的资料组不得自动归档，进入人工处理清单。

## 9. 后台维护任务

### 9.1 执行模型

- 单个后台工作器。
- 每批最多20个资料组。
- 批内严格串行，一次只处理一个资料组。
- 每批完成后暂停5秒，再读取下一批。
- 不允许浏览器触发全量扫描。
- 通过数据库锁或任务租约保证多进程部署时只有一个有效工作器。
- 每完成一个资料组即提交结果和进度，服务重启后从未完成项继续。

### 9.2 调度

- 服务正常运行期间以低优先级处理 `pending` 和可重试 `failed`。
- 每天 `00:00` 扫描所有尚未分析且符合资格的资料组并入队。
- 发布后执行一次全量维护，将所有符合资格的未分析、无法识别和异常资料组重新扫描。
- 全量维护仍遵守每批20个、串行、批间暂停5秒，不设置并行加速。
- 管理员可以暂停、继续和查看进度，但不能在前端执行识别计算。

### 9.3 资源保护

- 工作器进程优先级低于 API 请求。
- 配置单图超时、单组超时和最大图片像素。
- 记录批次 CPU 时间、失败原因和重试次数。
- 当系统负载超过配置阈值时暂停新批次，负载恢复后继续。
- 单组连续技术失败达到上限后转人工处理，不无限重试。

## 10. 页面展示

### 10.1 审阅工作台

- 资料组列表显示扫码进度 `0/3` 至 `3/3`。
- 机器通过的照片显示“扫码通过”标签。
- 保留“重新扫码”，请求只负责入队或扫描当前选定资料组，不在浏览器计算。
- 保留“人工确认”二次确认弹窗。
- 分类区域标题和操作语义调整为“纠正分类”。

### 10.2 数据中台

增加只读列：

- 扫码状态，与审阅工作台口径一致。
- 图片分类状态，显示完整、重复、缺失或数量异常。

### 10.3 驾驶舱

条码准确率只按符合扫描资格的资料组计算：

```text
准确率 = 当前有效 passed 或 manual_confirmed 数 / 已完成核验的符合资格资料组数
```

人工确认后的资料组计入通过，不再计入异常或无法识别。未满四张和分类不完整的资料组不进入分母，单独显示“不具备扫描条件”数量。

## 11. 测试策略

先补测试，再改实现，至少覆盖：

1. 只有四张有效照片且四类唯一时才进入扫描。
2. 少于四张、超过四张、重复分类和缺分类均为 `not_eligible`。
3. 三个期望值分散在四张照片中仍可 `3/3` 通过。
4. 额外无关条码和二维码不导致失败。
5. 条码和二维码机器匹配可直接通过。
6. OCR 候选未经确认不能通过或自动归档。
7. OCR 人工确认后可形成正式证据。
8. 修改照片、分类或三个身份字段后旧结果失效。
9. 人工确认后异常和无法识别统计同步移除。
10. 机器 `3/3` 且分类完整时自动归档。
11. 人工确认 `3/3` 且分类完整时自动归档。
12. 两个工作器竞争同一资料组时只归档一次。
13. 工作器每批最多20组、严格串行并在批间等待。
14. 服务重启后从未完成进度恢复。
15. 历史回填只更新 `unclassified`，不覆盖人工分类。
16. 工作簿双 Sheet 字段、固定值、文本格式和去重正确。
17. 照片 ZIP 路径、非法字符、扩展名和四类文件正确。
18. 缺少终端、表号、模块、采集器或四张照片时正式导出被阻止。
19. 现有已归档资料组不会被批量回退。
20. 任务领取、审阅、施工上传、KPI 和登录规则回归通过。

## 12. 发布与数据维护

- 版本：`V3.1.0`，从已发布 `production/V3/3.0.84` 创建 `production/V3/3.1.0`。
- 发布前备份 `.env`、`data`、`uploads` 和 PostgreSQL 数据库。
- 迁移先部署，工作器初始保持暂停；API 和页面验证通过后再启用。
- 先运行分类回填的只读预览，核对数量后执行正式回填。
- 再启动20组串行全量维护，观察 CPU、内存、数据库连接和 API 延迟。
- 发布包记录 SHA256，执行现有发布 SOP、客户端包校验和线上健康检查。
- 验证工作簿、ZIP、审阅状态、自动归档、驾驶舱统计和人工处理清单。
- 服务器只保留最近5个发布目录；旧版本由 GitHub 分支和标签保存。
- 回退程序时先暂停工作器；数据库迁移必须保持向后兼容，不删除历史识别或审计数据。
