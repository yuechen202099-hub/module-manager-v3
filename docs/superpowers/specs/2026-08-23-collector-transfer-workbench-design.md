# 采集器盘点、一次性替换池与甲方翻拍工作台设计

## 1. 目标

在 V3.2.5 现有 FastAPI、PostgreSQL、Vue 3 系统旁路新增一套“采集器中转”业务域，用现有施工数据生成终端级甲方录入清单，并解决现场采集器照片或编号错误的问题。

系统分成两个严格隔离的入口：

- 手机盘点页：扫描手上实物采集器，判断是否同号、是否需要补拍、是否进入替换池。这里绝不录入甲方平台。
- 桌面翻拍工作台：按终端依次展示可扫码的表号、模块号、采集器号和相应照片，由操作员用掌机翻拍后人工录入甲方平台。

不覆盖 `material_groups`、`photos` 中的原始施工编号和原始照片。最终提交编号、照片与原始需求之间通过新表映射，可审计、可回滚。

## 2. 已确认业务规则

1. 一个终端可包含多块电表。
2. 每块电表生成一条新装数据，只使用两个照片槽位：`module_meter`（电表和模块）和 `after_box`（改造完成）。
3. 拆除数据按终端内原采集器号去重，每个采集器只需要一张照片。
4. 终端所需采集器数等于终端内去重后的原采集器数。
5. 扫描到同号实物时优先直接匹配；已有可复用照片则不拍照，没有可用照片则补拍，但都不进入替换池。
6. 扫描到非同号实物时必须补拍，照片确认后才进入替换池。
7. 替换池状态为 `available -> reserved -> used`；同一实物采集器和同一张照片禁止重复使用。
8. 随机分配前锁定需求和候选池行。可用数量不足时整笔失败，禁止部分分配。
9. 随机结果持久化；刷新页面、并发请求或服务重启不得改变已分配结果。
10. 手机盘点与甲方平台无直接连接；甲方录入结果只由翻拍工作台人工勾选完成。
11. 所有号码按文本保存，保留前导零；同一团队内比较时使用去首尾空白后的完整编号，不套用电表长短码截取规则。

## 3. 数据边界

### 3.1 复用只读来源

- `projects`：项目范围和团队隔离。
- `material_groups`：终端、表号、安装地址和原始数据快照。
- `photos`：`module_meter`、`after_box` 以及照片上的原采集器号、模块号。
- `audit_logs`：记录运行创建、扫码决策、补拍、分配、完成与回滚事件。

### 3.2 新增旁路表

- `collector_transfer_runs`：一次数据快照/作业批次，保存项目、状态、统计和生成时间。
- `collector_transfer_terminals`：终端快照，保存地址、表计数、去重采集器需求数和工作台进度。
- `collector_meter_items`：每块电表的新装条目，保存原资料组、表号、模块号以及两张来源照片。
- `collector_requirements`：终端内去重后的拆除采集器需求，保存原编号和匹配状态。
- `collector_requirement_meters`：采集器需求与其服务电表的多对多快照。
- `physical_collectors`：手上实物采集器台账，编号在团队内唯一，保存盘点与池状态。
- `collector_photos`：实物采集器照片，保存原文件名、SHA256、存储位置和有效状态。
- `collector_scan_events`：每次网站扫码及系统判定，包含同号需求、是否要拍照和是否进池。
- `collector_assignments`：需求与实物采集器的一对一持久化分配，区分 `direct` 与 `random`。
- `collector_workbench_items`：甲方翻拍工作项，区分 `meter_install` 与 `collector_removal`，保存人工完成状态。

数据库唯一约束负责最终兜底：一个有效需求只能有一个有效分配；一个实物采集器只能被一个有效分配占用；团队内实物采集器号唯一；单个实物的有效照片 SHA256 不重复。

## 4. 数据生成

用户选择项目并创建运行后，系统在一个事务中读取现有资料组：

1. 按 `material_groups.terminal` 分组；空终端号作为诊断失败，不静默合并。
2. 每个资料组生成一个电表新装项。
3. 模块号优先取有效 `module_meter` 照片的 `asset_no`，再读取资料组快照中的兼容字段；缺失时保留为空并标记诊断。
4. 两个新装照片槽位只接受有效的 `module_meter` 与 `after_box` 照片；重复槽位按稳定排序选择一张并记录来源。
5. 原采集器号优先取有效照片的 `collector`，再读取资料组快照兼容字段。
6. 在每个终端内按完整原采集器号去重生成需求，并建立需求到所有关联电表的链接。
7. 运行保存生成时的快照，不随原始资料后续修改而隐式变化；需要刷新时显式新建运行。

生成结果若存在空终端、空表号、缺少两个新装照片槽位或空采集器号，不覆盖原数据。页面显示诊断，相关终端保持不可分配。

## 5. 手机扫码决策

扫码接口在同一团队和运行范围内执行：

1. 号码已登记：返回现有实物及照片状态，不创建重复台账。
2. 存在尚未匹配的同号需求：创建或复用 `direct` 分配。
   - 已有有效照片：`requires_photo=false`，可直接进入翻拍准备。
   - 无有效照片：`requires_photo=true`，照片补齐后进入翻拍准备。
   - 两种情况均 `add_to_pool=false`。
3. 不存在同号需求：登记为池候选，`requires_photo=true`、`add_to_pool=true`；照片未完成前状态不是 `available`。
4. 每次判断写入 `collector_scan_events`，重复扫码不会重复消耗需求或池资源。

手机拍照接口只接收图片，计算 SHA256 后写入受控存储。图片成功保存、数据库记录成功提交后，池候选才从 `awaiting_photo` 进入 `available`；任一步失败都不能出现“可用但无照片”的采集器。

## 6. 随机一次性分配事务

分配对象仅为尚未直接匹配且无诊断阻断的采集器需求。

事务顺序：

1. 按稳定顺序锁定本次运行的未匹配需求行。
2. 锁定同团队、有效照片齐全、状态为 `available` 的池采集器行。
3. 重新计算需求数与候选数。候选不足时返回 `409 pool_insufficient` 并回滚整笔事务。
4. 在事务内用安全随机源选择等量候选，逐条创建 `random` 分配并把实物状态改为 `reserved`。
5. 创建或刷新相应翻拍工作项后提交。数据库唯一约束阻止并发重复消耗。
6. 操作员完成对应拆除翻拍项时，实物采集器从 `reserved` 进入 `used`。

随机不表示不可追踪。每条分配必须保存原采集器号、最终实物采集器号、照片、操作者、时间和分配模式。

## 7. 翻拍工作台

工作台以终端为主列表，显示新装完成数、拆除完成数、阻断原因和总进度。

终端详情按固定顺序展示：

- 每块电表一个 `meter_install` 项：表号条码、模块号条码、`module_meter` 照片、`after_box` 照片。
- 每个去重采集器需求一个 `collector_removal` 项：最终采集器号条码和已绑定实物照片。

三个编号分别生成 Code 128 条形码，条码下方必须同时显示可人工核对的原始文本。页面只提供“上一项、下一项、标记已翻拍、撤销完成”；不提供甲方平台账号、表单或自动上传。

## 8. 逐个扫码初始化

新采集器台账只通过手机网站逐个扫码建立，不提供 Excel 或照片批量导入。

- 扫到同号采集器时，网站直接判断已有照片能否复用；能复用则无需拍照，也不加入替换池。
- 扫到同号但无可用照片时，只对当前采集器逐个补拍，完成同号直配，不加入替换池。
- 扫到非同号采集器时，只对当前采集器逐个补拍；照片确认后才加入一次性替换池。
- 已登记号码和相同 SHA256 照片继续复用现有幂等与去重规则。
- 系统原有总清单、施工资料等导入能力不受此业务边界影响。

## 9. 权限、安全与审计

- 所有 API 使用认证 token 中的 `team_id`，不信任请求体或查询参数传入的团队和操作者。
- 管理员可创建运行、执行随机分配和回滚；施工员与管理员可使用手机逐个扫码/补拍和翻拍工作台。
- 上传限制沿用系统图片大小、MIME 和存储安全规则；原始文件名只能作为展示和条码候选，不能直接作为路径。
- 页面、API 和审计日志不得记录甲方平台密码或会话。
- 新前缀 `/collector-transfer` 纳入生产认证中间件保护。

## 10. API 草案

- `POST /collector-transfer/runs`：由项目现有数据创建快照。
- `GET /collector-transfer/runs`：运行列表与统计。
- `GET /collector-transfer/runs/{run_id}`：运行诊断和终端汇总。
- `POST /collector-transfer/runs/{run_id}/scan`：手机扫码并返回同号/补拍/入池判定。
- `POST /collector-transfer/runs/{run_id}/collectors/{collector_id}/photo`：手机补拍。
- `POST /collector-transfer/runs/{run_id}/allocate`：整笔随机一次性分配。
- `GET /collector-transfer/runs/{run_id}/workbench`：终端工作台列表。
- `GET /collector-transfer/runs/{run_id}/workbench/{terminal_id}`：终端完整新装/拆除数据。
- `PATCH /collector-transfer/workbench/items/{item_id}`：标记完成或撤销。

## 11. 验收标准

- 一个终端多表且共享一个采集器时，只生成一个拆除需求。
- 同号扫码不进池；有照片不要求拍照，无照片只要求补拍。
- 非同号扫码在照片补齐前不可用，补齐后进入池。
- 池少于需求时无分配、无状态变化、无工作项变化。
- 两个并发分配请求不会重复使用同一采集器或同一需求。
- 刷新与重启后随机分配保持不变。
- 新装项严格只有 `module_meter` 和 `after_box` 两张来源照片。
- 手机页面无甲方平台录入入口；桌面工作台无自动上传。
- 手机页面无新采集器批量导入入口；已退役的 `/inventory/import` 返回 404。
- 原 `material_groups`、`photos` 编号、照片和分类保持不变。

## 12. 上线边界

本分支只完成本地代码、迁移文件和验证。生产迁移、发布、真实项目快照生成、真实照片导入和甲方平台操作都需要另行明确确认。
